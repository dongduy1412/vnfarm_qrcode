# Branded LCD QR — firmware 0.1.8

The check-in screen now uses the full 240 by 240 canvas, retaining the required
four-module white quiet zone. Module boundaries are distributed across the
canvas to avoid large unused margins from integer scaling. Dark red modules,
slightly rounded finder squares and the original user-supplied building icon
implement the approved design. Setup screens retain their Wi-Fi instructions.

The renderer uses error correction H and byte capacities for QR versions 17-20.
The enlarged approved logo spans 25 modules with a one-module white border,
roughly 29% of the version-17 code width (about 65 LCD pixels). This overlay
covers some alignment-pattern modules; the complete composited images are
decoded in the validation below. Inputs larger than 382 ASCII bytes are rejected. Logo pixels are
generated by `tools/generate_qr_logo.py` from the supplied PNG; the generated
80-by-80 RGB565 array is compiled into flash. No image model generates the QR modules.

`include/BrandedQr.h` is shared verbatim between firmware and the native preview
DLL. Build the native test from the project directory:

```powershell
python -m ziglang cc -O2 -c .pio/libdeps/s3tim/QRCode/src/qrcode.c -o .pio/qr-native.o
python -m ziglang c++ -shared -O2 -Iinclude -I.pio/libdeps/s3tim/QRCode/src tools/qr_preview_native.cpp .pio/qr-native.o -o .pio/qr-preview.dll
python tools/test_qr_render.py
```

Validation passed: 108 exact-payload decodes across independently signed sample
URLs, versions 17-20, original images, 90-degree rotations and mild blur.
Over-capacity input is rejected. Existing 23 protocol/web tests pass. The sample
preview uses a disposable test key, never the device private key.

Production s3tim build and COM5 upload passed, with flash hashes verified.
This upload does not erase the configuration/key NVS region. Phone-camera
scanning on the physical LCD remains a user validation step; decoded PNGs
cannot establish viewing-angle, glare or camera performance on hardware.
